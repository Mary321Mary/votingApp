# iOS: Swift Package Manager (no CocoaPods)

This project builds its iOS app **only** with Swift Package Manager (SPM), the
native package manager built into Xcode. There is no `Podfile`, no
`Podfile.lock`, no `Pods/` directory, no `Gemfile` and no `.xcworkspace` —
`open ios/votingApp.xcodeproj` (or `npm run ios`) is the whole setup.

The migration uses the SPM pipeline shipped with React Native 0.88
(`npx react-native spm …`). React Native ships prebuilt XCFrameworks instead of
compiling its core from source, so a clean build no longer runs CocoaPods or
Ruby at all.

## Layout

```
ios/
  votingApp.xcodeproj/            # the app project — three local package refs are injected here
    .spm-injected.json            # what `react-native spm add` injected (used by `spm deinit`)
  ReactNativeSPM/
    ReactNativeSPM.xcconfig       # generated: framework search paths, linker flags, flavor selection
    Scripts/sync-autolinking.sh   # build phase + scheme pre-action: re-runs codegen/autolinking when deps change
  build/                          # generated, git-ignored
    generated/autolinking/        #   the `Autolinked` package aggregating every native dependency
    generated/ios/                #   the `React-GeneratedCode` package (codegen + app dependency providers)
    xcframeworks/                 #   the `ReactNative` package exposing React headers + binary targets
    spm-artifacts/                #   downloaded React/ReactNativeDependencies/Hermes XCFrameworks (when bootstrapped locally)
```

The three local packages are referenced from `votingApp.xcodeproj`. They are
regenerated, not hand-edited.

## Everyday commands

```sh
npm install          # patches/, .env file, and the generated SPM packages on a fresh clone
npm run ios          # build & run on a simulator/device
npx react-native spm update   # refresh codegen + autolinking + framework slots after dependency changes
```

`npm install` runs three postinstall steps: `patch-package` (see below),
`scripts/generate-ios-config.js` (`.env`), and `scripts/ensure-ios-spm.js`,
which runs `npx react-native spm update` once if the generated packages under
`ios/build/` are missing (fresh clone). Set `SKIP_IOS_SPM_SETUP=1` to skip that
bootstrap. Do not use `npm ci --ignore-scripts`: the patched manifests are
required before an Xcode build can succeed.

Xcode builds are also self-healing: a scheme pre-action (and a build phase)
detects that `package.json`, `react-native.config.js`, `node_modules` or the
lockfile changed and re-runs codegen + autolinking. Editing `.env` is the one
input that build phase cannot see, because the value lives in
`react-native-config`'s generated file inside `node_modules`; run `npm run ios`
(or `node scripts/generate-ios-config.js`) after changing `.env`, or rely on
the copy generated by `npm install`.

## Native dependencies

React Native's SwiftPM autolinker needs a `Package.swift` inside every
autolinked npm package. Only `react-native-safe-area-context` ships one
upstream. For the other packages, `npx react-native spm scaffold` generated a
manifest from each podspec, and the results are committed as **patch-package**
patches in `patches/` because `node_modules` is not committed.

Patches also carry a few project-specific adaptations:

| Package | Adaptation |
| --- | --- |
| `react-native-maps` | Apple Maps only: the Google Maps subspec is excluded (`ios/AirGoogleMaps`), `HAVE_GOOGLE_MAPS` is pinned to `0`, and the Google-only privacy bundle stays out of the target. Add the Google SDK and re-enable the subspec if you ever need `PROVIDER_GOOGLE`. |
| `react-native-image-crop-picker` | `TOCropViewController` comes from its upstream Swift package (exact `2.8.0`, the range the podspec asked for) instead of CocoaPods trunk. The QBImagePicker storyboard + localizations are processed as resources and its runtime bundle lookup uses SwiftPM's bundle name. The unused vendored `QBImagePicker.framework` is excluded, and the flat `*Spec.h` / TOCrop includes are namespace-corrected. |
| `react-native-svg` | Metal filter libraries are bundled, the filter loader looks up SwiftPM's resource bundle name, and the `.metal` sources are excluded so the optional Xcode Metal toolchain is not required. |
| `react-native-config` | `GeneratedDotEnv.m` is generated by `scripts/generate-ios-config.js` (postinstall/preios) because SPM has no per-target script phases; the codegen spec is imported by its module-qualified name. |
| all scaffolded packages | `RCT_NEW_ARCH_ENABLED=1` and the standard `FOLLY_*` defines are added explicitly — they used to arrive via CocoaPods' `install_modules_dependencies` / `get_folly_config`. Headers that CocoaPods' header map resolved by bare name are wired with explicit header search paths, or imported module-qualified. |

A few SwiftPM mechanics that the scaffolded manifests have to reproduce from
CocoaPods:

- **Privacy manifests** (`PrivacyInfo.xcprivacy`) are picked up automatically
  from the target directory — declaring them in `resources:` duplicates them.
- **Resource bundles** are named `<Package>_<Target>.bundle`; libraries that
  hard-code a CocoaPods `resource_bundles` name need the `SWIFT_PACKAGE`
  conditional shown in the patches.
- **Header layout**: SwiftPM rejects a public-headers directory that contains a
  `<Target>.h` umbrella header next to subdirectories (such as the package's
  `.xcodeproj`). Those packages point `publicHeadersPath` at an empty
  `spm-public/` directory instead; no app code consumes their headers.
- **Localizations** must be declared with `.process`, and every package with
  localized resources needs `defaultLocalization`.

`react-native-render-html` is JS-only but ships an empty podspec; it is
excluded from iOS autolinking in `react-native.config.js`.

### Adding a native dependency

1. `npm install <package>`
2. `npx react-native spm scaffold` — writes a `Package.swift` (and possibly a
   `react-native-spm-prefix.h`) into the package, and records
   `swiftpmConfig.name` in its `package.json`.
3. Fix up the generated manifest if the podspec has features SPM cannot infer
   (subspecs, resources, external pods, build scripts) — compare with the
   adaptations above.
4. `npx patch-package <package>` and commit the new file in `patches/`.
5. `npx react-native spm update`, then build.

If the library later ships its own `Package.swift`, remove its patch.

### Upgrading a dependency

`patches/*.patch` are tied to exact versions. When you bump a package, delete
its old patch, repeat the steps above and commit the new patch. A failed patch
makes `npm install` fail loudly instead of silently producing an unbuildable
project.

## React Native / Xcode CLI patch

`patches/@react-native-community+cli-config-apple+20.2.0.patch` backports the
SPM project detection that landed after CLI 20.2.0. Without it, the CLI only
recognises an iOS project when a `Podfile` exists, so `react-native config`,
`react-native run-ios` and the build-time autolinking sync fail on a
CocoaPods-free project. The patch looks for the `.spm-injected.json` marker
inside a `.xcodeproj` — the same check upstream added. Remove the patch once
`@react-native-community/cli-config-apple` reaches a release that contains it.

## The React Native framework artifacts

`ios/build/xcframeworks` points at per-configuration `React`, `Hermes` and
`ReactNativeDependencies` XCFrameworks downloaded from Maven
(`repo.reactnative.dev`, with Maven Central as fallback). They are cached under
`~/Library/Caches/ReactNative/` by default. To pre-fetch or to point at a local
mirror:

```sh
node node_modules/react-native/scripts/setup-apple-spm.js download
# or, offline-friendly and CI-safe, with a workspace-local cache:
RCT_SKIP_CACHES=1 npx react-native spm update --artifacts "$PWD/ios/build/spm-artifacts"
```

The artifacts are build-time downloads, not CocoaPods trunk dependencies:
nothing in this repository fetches from the CocoaPods registry anymore.

## Reverting

`npx react-native spm deinit` removes the injected package references and
build phases from the `.xcodeproj`. Reverting the migration itself is a normal
`git revert` of the migration commit.
